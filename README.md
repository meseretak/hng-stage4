# SwiftDeploy — Stage 4A

SwiftDeploy is a declarative stack manager. Instead of writing config files by hand, you describe your entire deployment in one file — `manifest.yaml` — and the CLI tool handles everything else: generating configs, building containers, health checking, and mode switching.

`manifest.yaml` is the single source of truth. You never edit `nginx.conf` or `docker-compose.yml` directly. The tool generates them.

---

## Project Structure

```
hng-stage4/
├── manifest.yaml                  ← the only file you edit
├── swiftdeploy                    ← the CLI tool (Python)
├── Dockerfile                     ← builds the app image
├── app/
│   ├── main.py                    ← Flask API (stable + canary mode)
│   └── requirements.txt
├── templates/
│   ├── nginx.conf.j2              ← Nginx Jinja2 template
│   └── docker-compose.yml.j2     ← Compose Jinja2 template
└── README.md

Generated (not committed to git):
├── nginx.conf                     ← generated by swiftdeploy init
└── docker-compose.yml             ← generated by swiftdeploy init
```

---

## How It Works

```
manifest.yaml
     │
     ▼
swiftdeploy init
     │
     ├──► nginx.conf          (from templates/nginx.conf.j2)
     └──► docker-compose.yml  (from templates/docker-compose.yml.j2)
               │
               ▼
         docker compose up
               │
         ┌─────┴──────┐
         │  swiftdeploy-app   (Flask on port 3000, internal only)
         │  swiftdeploy-nginx (Nginx on port 8080, public)
         └────────────┘
```

All traffic goes through Nginx. The app port is never exposed directly.

## Setup — Fresh Server

### 1. Clone the repo

```bash
git clone https://github.com/meseretak/hng-stage4.git
cd hng-stage4
```

### 2. Install CLI dependencies

```bash
pip install pyyaml jinja2
```

### 3. Make the CLI executable

```bash
chmod +x swiftdeploy
```

### 4. Build the app image

The image must be built before deploying. It uses Python 3.12 Alpine (under 300MB), runs as a non-root user, and includes a built-in healthcheck.

```bash
docker build -t swift-deploy-1-node:latest .
```

### 5. Deploy

```bash
./swiftdeploy deploy
```

The stack is now live at `http://<your-server-ip>:8080`

> Make sure port 8080 is open in your firewall / EC2 security group.

## Subcommand Walkthrough

### `swiftdeploy init`

Reads `manifest.yaml` and generates two files from Jinja2 templates:
- `nginx.conf` — from `templates/nginx.conf.j2`
- `docker-compose.yml` — from `templates/docker-compose.yml.j2`

```bash
./swiftdeploy init
```

Expected output:
```
──────────────────────────────────────────────────────
  swiftdeploy init
──────────────────────────────────────────────────────
  →  Loading manifest.yaml ...
  ✔  Generated nginx.conf
  ✔  Generated docker-compose.yml

init complete.
```

> The grader will delete the generated files and re-run this command to verify they regenerate correctly.

---

### `swiftdeploy validate`

Runs 5 pre-flight checks before deploying. Exits non-zero if any check fails.

```bash
./swiftdeploy validate
```

| Check | What it verifies |
|---|---|
| 1 | `manifest.yaml` exists and is valid YAML |
| 2 | All required fields are present and non-empty |
| 3 | The Docker image referenced in the manifest exists locally |
| 4 | The Nginx port is not already bound by another process |
| 5 | The generated `nginx.conf` has no syntax errors |

Expected output (all passing):
```
  Check 1: manifest.yaml exists and is valid YAML
  ✔  manifest.yaml exists and is valid YAML

  Check 2: All required fields present and non-empty
  ✔  All required fields present and non-empty

  Check 3: Docker image exists locally
  ✔  Image 'swift-deploy-1-node:latest' found locally

  Check 4: Nginx port 8080 not already bound
  ✔  Port 8080 is available

  Check 5: nginx.conf is syntactically valid
  ✔  nginx.conf syntax is valid

  ✔ ALL CHECKS PASSED
```

---

### `swiftdeploy deploy`

Runs `init`, brings up the full stack with `docker compose up`, then blocks and polls `/healthz` every 3 seconds until the stack responds or 60 seconds pass.

```bash
./swiftdeploy deploy
```

Expected output:
```
  →  Running init ...
  →  Bringing up stack ...
  [+] up 2/2
  ✔  Container swiftdeploy-app    Healthy
  ✔  Container swiftdeploy-nginx  Running
  →  Waiting for health check at http://localhost:8080/healthz (timeout: 60s) ...
  ✔  Stack is healthy at http://localhost:8080/healthz

  ✔ DEPLOY COMPLETE
```

---

### `swiftdeploy promote`

Switches the app between `stable` and `canary` mode without restarting Nginx.

What it does internally:
1. Updates the `mode` field in `manifest.yaml`
2. Regenerates `docker-compose.yml` with the new `MODE` env var
3. Restarts only the app container (`--no-deps`)
4. Hits `/healthz` to confirm the new mode is active

```bash
# Switch to canary
./swiftdeploy promote canary

# Switch back to stable
./swiftdeploy promote stable
```

Expected output:
```
  →  Current mode: stable  →  New mode: canary
  ✔  Updated manifest.yaml: mode = canary
  →  Restarting app container ...
  →  Confirming new mode via http://localhost:8080/healthz ...
  ✔  Mode confirmed: canary

  ✔ PROMOTE COMPLETE — mode is now 'canary'
```

Confirm via curl:
```bash
curl http://localhost:8080/healthz
```
```json
{
  "status": "ok",
  "mode": "canary",
  "version": "1.0.0",
  "uptime_seconds": 42.3
}
```

---

### `swiftdeploy teardown`

Stops and removes all containers, networks, and volumes.

```bash
# Stop everything
./swiftdeploy teardown

# Stop everything AND delete generated config files
./swiftdeploy teardown --clean
```

## API Endpoints

The app runs as a Flask service on port 3000 internally. All requests go through Nginx on port 8080.

### `GET /`

Returns a welcome message with the current mode, version, and timestamp.

```bash
curl http://localhost:8080/
```
```json
{
  "message": "Welcome to SwiftDeploy API",
  "mode": "stable",
  "version": "1.0.0",
  "timestamp": "2026-05-04T12:00:00Z"
}
```

### `GET /healthz`

Liveness check. Returns status and how long the app has been running.

```bash
curl http://localhost:8080/healthz
```
```json
{
  "status": "ok",
  "mode": "stable",
  "version": "1.0.0",
  "uptime_seconds": 120.5
}
```

### `POST /chaos`

Simulates degraded behaviour. Only available in canary mode. Stable mode returns 403.

**Slow responses** — sleep N seconds before every response:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "slow", "duration": 3}'
```

**Random errors** — return HTTP 500 on ~50% of requests:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'
```

**Recover** — cancel any active chaos:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

---

## Canary Mode

When the app runs in canary mode, every response includes an extra header:

```
X-Mode: canary
```

This header is forwarded through Nginx to the client. You can verify it:

```bash
curl -I http://localhost:8080/
```

## manifest.yaml Reference

This is the only file you edit. Everything else is derived from it.

```yaml
services:
  app:
    image: swift-deploy-1-node:latest   # Docker image name (must exist locally)
    port: 3000                           # Internal port the app listens on
    mode: stable                         # stable or canary
    version: "1.0.0"                     # Injected as APP_VERSION env var
    restart: unless-stopped

  nginx:
    image: nginx:latest
    port: 8080                           # External port exposed to the world
    proxy_timeout: 30                    # Proxy timeout in seconds

network:
  name: swiftdeploy-net                  # Docker network name
  driver_type: bridge                    # Network driver
```

## Security Practices

- App runs as a non-root user (`appuser`) inside the container
- All Linux capabilities are dropped; only `NET_BIND_SERVICE` is added back for the app
- Nginx gets `CHOWN`, `SETUID`, `SETGID` to manage its worker processes
- `no-new-privileges` is set on both containers
- The app port (3000) is never published — only Nginx port (8080) is exposed
- Image is based on `python:3.12-alpine` — well under 300MB

## Nginx Access Log Format

Logs are written in this format:

```
$time_iso8601 | $status | ${request_time}s | $upstream_addr | $request
```

Example:
```
2026-05-04T12:00:01+00:00 | 200 | 0.002s | 172.18.0.2:3000 | GET /healthz HTTP/1.0
```

View live logs:
```bash
docker logs swiftdeploy-nginx
```
